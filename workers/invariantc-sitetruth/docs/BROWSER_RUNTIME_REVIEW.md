# Hosted browser runtime and egress review — SiteTruth

**Reviewed:** 2026-10-08

**Decision:** No browser runtime is approved for customer scanning. Cloudflare Containers is the preferred candidate for an isolated egress prototype; destination-IP pinning and runtime security testing remain open. Hosted URL scanning remains disabled.

**Prototype update (2026-10-08):** The default-deny Container/Worker harness in [`EGRESS_DENY_PROTOTYPE.md`](EGRESS_DENY_PROTOTYPE.md) includes a fixed `example.com` TLS handshake-only path. Source validation now rejects private, metadata, reserved, documentation, multicast, and other IANA special-purpose IPv4 answers before connecting, and the egress policy checks the returned address evidence again. The TLS socket explicitly checks the peer certificate against `example.com` and sets that name for SNI. Tests cover matching/wrong host certificates, those address ranges, mixed public/special answer sets, selected-IP connection parameters, peer-address mismatch, and failure handling. Its Linux Docker/Workerd CI execution is pending; the current local Wrangler dry-run stopped before bundling because Docker is missing. Until a hosted run is observed, no Container runtime behavior is established. The probe sends no HTTP request to the site and is not Chromium or a general scanner, so it does not change the decision above. Cloudflare currently documents the `durable_object` scheduling policy as public beta and notes that deployed processes under this policy retain root Linux capabilities even when `exec()` specifies another UID/GID.

## Scope

This review compares Cloudflare Browser Run and Cloudflare Containers using Cloudflare's current primary documentation. It does not create a binding, start a container/browser session, consume paid usage, or establish security properties that have not been independently demonstrated. This is an architecture review, not a security approval.

## Cloudflare Containers — preferred prototype candidate

Containers can run a Linux browser image under Worker and Durable Object control. The documented egress controls offer a stronger prototype boundary than Browser Run's hostname-only guardrails:

- Set `enableInternet = false` at container start. Cloudflare documents that unapproved traffic cannot leave, non-HTTP ports are blocked, and DNS lookups do not reach a public resolver. A catch-all outbound handler can receive HTTP and HTTPS requests from the container when HTTPS interception is enabled. See [Container outbound traffic](https://developers.cloudflare.com/containers/configuration/outbound-traffic/).
- For a new prototype, use the Durable Object Container API with `enableInternet = false`, `interceptAllOutboundHttp()`, and `interceptOutboundHttps("*")`, wired to a deny-by-default `WorkerEntrypoint`. The `Container` class alternative requires exporting `ContainerProxy`, setting `interceptHttps`, and trusting Cloudflare's ephemeral CA in the container's runtime trust store at startup; do not bake that ephemeral certificate into the image. Route all HTTP/S requests to trusted Worker code and provide no pass-through path for unhandled requests. Exercise the exact API and Chromium image before relying on the behavior. See the [Durable Object Container API](https://developers.cloudflare.com/containers/api/durable-object-container/).
- This is a promising enforcement boundary, but it does not yet prove the required checked-address guarantee. A Worker handler that validates DNS and then calls ordinary `fetch()` does not demonstrate that the connection uses the same checked IP. Cloudflare documents that Workers cannot `fetch()` a literal IP URL, and `cf.resolveOverride` only works when both hostnames are in the Worker's zone. The repository now has a fixed-host TLS-only implementation, but its actual runtime result is pending; safe HTTP streaming and redirect-by-redirect address revalidation remain unimplemented. See [Workers request routing](https://developers.cloudflare.com/workers/runtime-apis/request/), [Workers fetch limitations](https://developers.cloudflare.com/workers/platform/known-issues/), and [Workers TLS](https://developers.cloudflare.com/workers/runtime-apis/nodejs/tls/).
- The fixed-host probe is a first architecture experiment, not release evidence until the CI result is reviewed. It resolves A records with `node:dns`, rejects any answer in the current IANA IPv4 special-purpose registry, connects to the selected remaining IPv4 using `node:tls.connect`, sets SNI, and explicitly applies `tls.checkServerIdentity("example.com", cert)`. Cloudflare documents `node:dns` resolution via DNS over HTTPS and supports `resolve4`; it documents `node:tls.connect`, `tls.checkServerIdentity`, and `TLSSocket` support. This path still needs an observed Container run, runtime negative cases for wrong-host and invalid-chain certificates, and all-address revalidation for a general target. See [Cloudflare Workers DNS](https://developers.cloudflare.com/workers/runtime-apis/nodejs/dns/), [Cloudflare Workers TLS](https://developers.cloudflare.com/workers/runtime-apis/nodejs/tls/), [Node.js TLS identity checking](https://nodejs.org/api/tls.html#tlscheckserveridentityhostname-cert), and the [IANA IPv4 special-purpose registry](https://www.iana.org/assignments/iana-ipv4-special-registry).
- A complete probe must record a normalized `TLSSocket.remoteAddress` equal to the selected checked address, the expected `socket.servername`, `socket.authorized === true`, and successful hostname validation using the normal trusted CA set. Then test the HTTP layer separately: send the canonical `Host` authority, stream within explicit byte/time limits, do not follow redirects automatically, and resolve/revalidate/pin each new destination before opening another socket. Any mismatch, unsupported API behavior, interception incompatibility, or inability to observe the peer address rejects this design; use a separately managed egress proxy with an independently enforced network boundary instead.
- Therefore the prototype must prove that the trusted egress handler connects only to each address it checked, preserves the requested hostname for SNI and certificate verification, and applies the rule to every redirect, subresource, popup, and WebSocket attempt. If this cannot be demonstrated, use a separately managed egress proxy with an independently enforced network boundary.

### Container cost and sizing

Containers are available on Workers Paid. Cloudflare's current pricing states that the $5/month Workers Paid plan includes 25 GiB-hours of provisioned memory, 375 vCPU-minutes of active CPU, and 200 GB-hours of provisioned disk. Additional usage is billed at $0.0000025 per GiB-second of memory, $0.000020 per vCPU-second, and $0.00000007 per GB-second of disk. Container egress is priced by region: North America/Europe is $0.025/GB with 1 TB included; Oceania/Korea/Taiwan is $0.05/GB with 500 GB included; everywhere else is $0.04/GB with 500 GB included. Workers and Durable Objects have separate usage charges. Available instance types include `lite` (256 MiB), `basic` (1 GiB), and sizes up to `standard-4` (12 GiB). See [Container pricing](https://developers.cloudflare.com/containers/platform/pricing/) and [limits and instance types](https://developers.cloudflare.com/containers/platform/limits/).

No per-scan or monthly estimate is approved. Measure browser image size, provisioned memory and disk, active CPU time, session duration, egress volume, region, Worker/DO operations, and idle timeout in an approved staging experiment, then apply an operator-approved ceiling and billing alerts.

## Browser Run — alternative candidate, not approved

- Browser Run provides managed Chromium sessions through a Workers binding. Session guardrails restrict HTTP and HTTPS requests by hostname and are unavailable for Quick Actions. If both allowlist properties are omitted, requests are unrestricted. The published guardrail policy is hostname-based; this review did not find documentation establishing rejection of all private/reserved/metadata destinations or address pinning. See [Browser Run guardrails](https://developers.cloudflare.com/browser-run/features/guardrails/) and the [Browser binding API](https://developers.cloudflare.com/browser-run/reference/browser-binding-api/).
- `outboundByHost` routes selected hostnames through a Worker Fetcher for HTTP only. HTTPS requests do not use that outbound Worker, and unmapped hostnames use the browser's normal network path. It does not establish the required all-request HTTPS egress boundary. See [Browser Run outbound Workers](https://developers.cloudflare.com/browser-run/features/outbound-workers/).
- Current published Workers Paid pricing includes 10 browser-hours/month, then $0.09 per additional browser-hour. Browser Sessions include 10 average concurrent browsers, then $2 per additional average concurrent browser. The Free plan is 10 browser-minutes/day and three concurrent sessions. Recheck the account plan and current pricing before use. See [Browser Run pricing](https://developers.cloudflare.com/browser-run/pricing/) and [limits](https://developers.cloudflare.com/browser-run/limits/).
- Cloudflare announced Browser Run guardrails on Sep 14, 2026. Validate their behavior in a disposable approved staging environment before relying on them. See the [Browser Run changelog](https://developers.cloudflare.com/changelog/product/browser-run/).

## Required work before hosted scans

1. Observe the isolated fixed-host TLS handshake-only prototype in the Linux Docker/Workerd CI job and review the logs/evidence. This is a required architecture check, not customer scan evidence.
2. Build an isolated Container-based Chromium prototype with internet disabled, HTTPS interception enabled, no direct public DNS, no non-HTTP egress, a default-deny Worker handler, and one short-lived container per scan or another reviewed isolation boundary. Add controlled valid-host, wrong-host, and invalid-chain TLS cases in that trusted Worker/Container path.
3. If the runtime checks pass, implement and demonstrate address-pinned outbound HTTPS with hostname/SNI verification. Test DNS rebinding, private/reserved IPv4 and IPv6, mapped/alternate numeric addresses, metadata endpoints, redirects, subresources, WebSockets, DNS, UDP/QUIC, unexpected ports, and direct egress.
4. Verify that TLS interception works with the chosen Chromium image and that customer site behavior remains representative. Independently review the security design and test evidence.
5. Measure real container/Worker/DO and egress usage, set operator-approved tenant/account limits, cost alarms and ceilings, and validate cleanup/termination on every job outcome.
6. Keep `DOMAIN_VERIFICATION_ENABLED` and `ARTIFACT_RETENTION_ENABLED` false and add no runtime binding until the egress, data, cost, and operational gates pass.

Until those gates pass, staging remains an API-only evaluator. No Container or Browser Run binding, customer website, customer payload, or paid browser session was used in this review.
